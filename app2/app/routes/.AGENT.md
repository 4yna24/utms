# Routes Directory — Coding Rules

**Location**: `app/routes/`  
**Purpose**: HTTP request/response layer (thin controller only)  

## Structure

```
routes/
  __init__.py     # register_blueprints()
  common.py       # @login_required, @role_required decorators
  admin.py        # Admin API: role changes, backup, restore (prefix: /api/admin/)
  auth.py         # Login, register, logout (includes /auth/admin/login)
  applicant.py    # Applicant operations
  dean.py         # Dean operations
  oidb.py         # OIDB operations
  ydyo.py         # YDYO operations
  ygk.py          # YGK operations
  dashboard.py    # Dashboard route (all roles)
```

## Auth Route Map

| Endpoint | Who uses it | Role selector |
|---|---|---|
| `/auth/applicant/login` | Applicants | No |
| `/auth/applicant/register` | Applicants | No (open self-registration) |
| `/auth/staff/login` | Staff (oidb, dean, ygk, ydyo) | Yes — no register link shown |
| `/auth/staff/register` | **Disabled** — redirects to staff login | — |
| `/auth/admin/login` | Admin only | No — role is hardcoded "admin" |

Admin is **not** in `_STAFF_SLUGS` — the staff login rejects it. Admin has its own login route, not linked from the public portal. Navigate to it directly.

Staff self-registration is disabled. Staff accounts must be provisioned by an admin (see TODO in `app/AGENTS.md`).

## Dean Routes (`/api/dean/`)

| Endpoint | Method | Description |
|---|---|---|
| `/check-applicants` | GET | Standalone applicant list view |
| `/return/<id>` | POST | Return to applicant/OIDB/YDYO with `return_target` + `dean_notes` form fields |
| `/forward-to-ygk/<id>` | POST | Forward to YGK with faculty selection |
| `/forward-all-to-ygk` | POST | Auto-forward all to YGK (not yet implemented) |

**Return target → status mapping** (enforced in `DeanOffice.return_application`):

| `return_target` value | Resulting status |
|---|---|
| `applicant` | `returned` |
| `oidb` | `submitted` |
| `ydyo` | `forwarded_to_ydyo` |

`dean_notes` is stored on the application and displayed as a yellow banner in the receiving role's panel (OIDB, YDYO) and in the applicant's track view.

## EXPLICIT CODING RULES

### ✅ DO:
1. **Delegate to services or role classes** — routes call one method and handle the result
2. **Use `@role_required("slug")`** — all non-auth routes protecting a role must use this decorator
3. **Flash static success messages** — hardcoded strings, not extracted from result.data
4. **Flash `result.error_msg` for errors** — the business layer already formatted it
5. **Redirect after POST** — always redirect after successful mutations (PRG pattern)

### ❌ DO NOT:
1. **Direct database access** — never use `db.session`, `ApplicationORM.query`, etc.
2. **Business logic** — no form validation, no status checks, no complex conditions
3. **Direct class instantiation in routes** — instantiate inside a `_svc()` / `_admin()` helper, not inline
4. **isinstance checks on result.data** — the OperationResult contract guarantees the type
5. **Extract messages from result.data** — `result.data.get("message")` is wrong; use static flash

## Pattern: Correct Route

```python
@admin_bp.route("/users/change-role", methods=["POST"])
@role_required("admin")
def change_user_role():
    try:
        target_id = int(request.form.get("user_id", 0))
    except ValueError:
        flash("Invalid user ID.", "error")
        return redirect(url_for("dashboard.index"))

    new_role = (request.form.get("new_role") or "").strip()
    result = _admin().change_user_role(target_id, new_role)

    if result.success:
        flash(f"Role updated to '{new_role}'.", "success")   # static message
    else:
        flash(result.error_msg, "error")                     # from OperationResult

    return redirect(url_for("dashboard.index"))
```

## Dashboard Route (`dashboard.py`)

`_get_role_data(role_slug, user_id, email)` returns a dict that is spread into `render_template`. Add a new branch here when a new tab needs data. Admin has its own branch that returns `admin_users`, `admin_config`, `admin_applications`, `admin_backups`.

Role display name lookup uses `_ROLE_DISPLAY` (a local dict) rather than `ROLE_DEFINITIONS`, so admin shows "Administrator" without being added to the public portal's role list.

## Anti-Pattern: What NOT to Do

```python
# ❌ WRONG — direct class use with inline instantiation
applicant = Applicant(session["user_id"], session["user_email"], "applicant")
form_data = applicant.parse_form_data(request.form)   # form parsing in route

# ❌ WRONG — direct database
from app.models import ApplicationORM
app = ApplicationORM.query.get(id)
app.status = "new_status"
db.session.commit()

# ❌ WRONG — extracting message from result.data
if result.success:
    flash(result.data.get("message"), "success")   # ApplicationORM has no .get()
```
